# RTC 启动时间的消费者边界

日期：2026-10-04。此增量已配合RTC启动采用合入，HTTP/状态/动作/Web和七项真实SNTP/事件消费者在r43相关模块通过，七消费者在r45再次通过；原整体FAIL及后继夹具修正各自保全。此处为Host局部证据，不是完整构建、部署、走时精度或电池保持验收。

RTC 启动采用只提供有效日历：`timeSource=rtc`、`timeQuality=rtc_unverified`、`synced=false`、`timeSourceAuthenticated=false`。`rtcBootStatus=applied`表示这次启动采用成功，不是最近校准时间。来源年龄表示本次采用后的单调时间，不证明 RTC 电池、漂移或绝对时间可信。

| 消费路径 | RTC 启动时间的行为 |
| --- | --- |
| 系统时间 API / Web | 有效本地日历可显示，明确标为 RTC 启动时间（未校准），不显示网络同步成功或 TLS 来源。后续来源失效/变化清除旧提示。 |
| SNTP 等待与后台同步任务 | 同步成功要求 `synced=true`及新的来源序号；RTC 序号变化本身不会使等待成功，也不会触发后台同步成功事件。 |
| HTTPS 时间接口 | 原先只检查 epoch 下界，会让未校准 RTC 日历跳过时间 bootstrap。现在无有效同步记录时走既有 SNTP bootstrap；失败时不开始 HTTPS 请求。原 CA 包、证书检查和超时保留。 |
| RTC 复制系统时间（动作 37） | RTC-only来源被`DS1302_SYSTEM_TIME_UNSYNCED`拒绝，在读取/写入 RTC 前返回，不把 RTC 读回值又当校准写回。来源新鲜度、时区锁与写后核验仍按原流程。 |
| SD 连续记录 | 可保留 RTC 来源质量，但`wallEpochMs=null`。记录时间不会伪装为已经同步的绝对采样时间。 |
| 每日时间点规则 | 既有调度只检查系统本地日历可转换，不要求`synced=true`。启用 RTC 启动采用后，原来等待无效系统时钟的每日规则可能开始匹配；因此采用 RTC 日历不只是展示变化，应一并核对已启用的每日规则、时区与输出。此增量未改变该调度策略。 |

## 可选网络同步后写回规则

[禁用示例](rtc-ntp-writeback-disabled-example-20261004.json)通过已有`ntp_synced`事件（triggerType 4）执行动作 37；目标`rtc_demo`是占位符，参数固定`system-local`，拒绝以事件载荷替代动作参数。示例不启用、不上报、不写数值历史、不允许面板控制，也没有导入到任何现场设备。

该事件由后台接受的网络时间同步或已通过请求匹配检查的 MQTT 时间响应触发；事件名字沿用`ntp_synced`，并不证明来源认证或真实时间准确。Web“同步时间”接口目前不直接发布这个事件，不能承诺按按钮立即写回 RTC。RTC 启动采用本身也不发此事件。

正式启用前应核对部署候选、设备身份、DS1302目标、显式 RTC 时区偏移与系统活动时区、来源策略和配置保全。动作 37复制系统本地日历，因此应保持两端日历时区约定一致；暂停位保持原状。执行时若来源过期或改变，会拒绝或报告写后无法确认；后者可能已经写入，不保证回滚，也不自动重试。

## 验证边界

准备了16项新增Host用例：HTTPS RTC bootstrap成功/失败、未知时间bootstrap、已有同步不重复bootstrap；共享时间状态；RTC-only禁止写回；三组真实Web渲染；真实SNTP等待两组；静态事件目录、真实调度入口与规则匹配五组。网络、系统时钟、GPIO、任务队列均为显式夹具边界；规则匹配只观察入队参数，不实际写 RTC。

这些用例已取得r43/r45相关模块证据，输入及原报告见相应focused独立保全目录；它们不是完整候选PASS。完整候选门禁、浏览器视觉、板上启动、实体显示、RTC校准/电池保持、SD实卡及24h/7d/V14仍须各自验收。
