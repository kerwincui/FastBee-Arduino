## 1. 审核摘要

项目已经具备零代码嵌入式物联网平台的主体结构，不建议推倒重建。当前最需要的是把已有能力做成可验证、可迁移、资源可控的完整产品链路，而不是继续单纯增加外设类型名称。

本计划围绕四个目标展开：

1. **跨开发板**：芯片能力、整板接线、资源占用、驱动能力分别描述；更换板卡时尽量只调整板卡模板与接线映射。
2. **常用硬件零代码**：功能配置 → 外设配置 → 外设执行 → 数据/事件 → 联动/展示/上报 → 诊断，逐项验收闭环。
3. **按需内存**：区分编译裁剪、用户启用、依赖/预算准入、实例初始化、运行降级；“关闭选项”不直接等于“内存已经释放”。
4. **长期稳定**：以内部 DRAM、最大连续块、任务栈、队列上限、失败恢复和持续运行证据评价，而不是只看总可用堆或一次成功演示。

支持范围必须分级：首先稳定现有 ESP32、ESP32-C3、ESP32-C6、ESP32-S3 构建族；同芯片的不同开发板仍需单独核对接线、电源、外扩芯片和保留资源。其他 MCU 架构属于后续独立可行性工作，不承诺通过一份 JSON 直接适配。

需要保留的优势是统一配置/执行架构、现有资源保护、已经接入的驱动以及分层测试基础。最有价值的改进不是推倒重建，而是让这些基础具备一致的能力边界、生命周期、诊断和验收证据。

### 1.2 产品目标与取舍原则

- **零代码有明确适用范围**：对已支持板卡、驱动和应用场景，用户无需编写 C++、脚本或 JSON；接线、供电和必要标定仍需按说明完成。未知芯片/协议由开发者扩展后再进入支持目录。
- **数量不作为主要成熟度指标**：外设枚举数、页面数、通过的源码字符串检查数不能代替真实可用场景和故障恢复能力。
- **稳定不等于全功能同时开启**：按板型和资源给出可运行组合、容量与频率；额定组合不能靠反复暂停核心采集或定时重启维持。
- **增量治理优先**：先补行为测试和接口契约，再局部拆分大文件；同时避免持续向核心管理器堆特例。
- **产品承诺以证据为准**：从“开发者自己能使用”推进到“其他用户可独立配置、理解故障并恢复”，而不是仅完成新增驱动的正常路径演示。

## 6. 主要发现与风险分级

优先级：P0 为下一阶段必须先解决的可信性/安全基础，P1 为主体产品化能力，P2 为按需求扩展。P0 不表示已经证实发生安全事故。

| 编号 | 优先级/性质 | 发现与依据 | 建议处理 |
| --- | --- | --- | --- |
| R01 | P0，已证实覆盖缺口 | 九环境覆盖四个芯片家族，但 `BoardProfileId` 只有普中 ESP32、C6 DevKit、通用 S3；C3 在 `compiledBoardProfileSupported()` 返回 false，外设预检接口返回 501 | 补 C3；拆清通用芯片能力与特定板卡接线；未知板卡不能冒充已验证整板 |
| R02 | P0，已证实门禁失败 | 第 5 节通用架构检查失败 | 能力分支收口，保留诊断功能并回归；不自动修改现有未提交工作 |
| R03 | P1，已证实能力边界 | CAN、USB、CAMERA、GPIO_TOUCH 等有类型定义，但不在当前 `isPeripheralTypeImplemented()` 成功分支；外设 ETHERNET 类型也不等于网络 W5500 适配器 | 保留现有 `implemented` 标识与失败关闭机制，统一发布能力清单；不得按枚举数量宣传支持数量 |
| R04 | P1，已证实容量约束 | `MAX_SENSOR_DRIVERS=8`，当前源码已有 7 个注册名（含 SHT30/SHT31）；功能元数据目前 27 项，快照掩码上限 32 | 新驱动先处理注册容量/溢出诊断；型号优先归已有功能组，不为每个型号新建常驻功能对象 |
| R05 | P0，待验证生命周期风险 | 功能 Flash/RAM 来自静态元数据；`active` 是门控结果，不是全部硬件实例运行证明；`pendingRestart` 等字段目前对 I²C/扩展 IO 特别处理 | 全功能统一“期望/启动快照/已初始化实例/降级/待重启”；关闭后的 RAM 回收必须按生效方式验证 |
| R06 | P0，待验证资源风险 | I²C 已有 owner、互斥、延迟释放与恢复；但目前围绕单个 `Wire`。SPI 初始化分散在通用 SPI、RFID、SD、TFT 等路径 | 先核实同总线共存、锁顺序和释放；资源规划与真实总线所有权统一，再按板卡需要扩第二 I²C/共享 SPI |
| R07 | P1，已证实建模粒度限制 | `ResourceProfile` 的外设/规则容量主要按芯片族分档，S3 无 PSRAM 与带 PSRAM 共用相同数量上限；运行时另有预算保护 | 容量按实际 DRAM、PSRAM 可用性、驱动实例成本与组合负载评估；不能直接把“32 个”当成任意 32 个都可运行 |
| R08 | P0，待验证长稳风险 | 已有内存保护、固定工作池、有限队列、退避、观测质量与失鲜；但这些机制存在不代表长期组合运行通过 | 建立每种负载的资源基线、故障注入、恢复和长稳证据；不靠持续暂停业务或定时重启算通过 |
| R09 | P1，待补齐零代码闭环 | RTC、SD、通用 UART/SPI 等已有部分驱动/接口；当前执行器没有清晰独立的 RTC 校时、SD 数据记录动作分派 | 专项确认现有可调用能力，补类型化动作、字段绑定与限制；“可手动操作”与“可配规则自动运行”分开 |
| R10 | P1，已证实维护成本 | 当前 `PeripheralManager.cpp` 4758 行、`PeriphExecManager.cpp` 4422 行、外设路由 4410 行、执行器 2731 行 | 先冻结行为测试，再按驱动生命周期、描述符、协议动作拆分；不先大规模重写核心管理器 |
| R11 | P1，已证实文档漂移 | README 前部列九环境和 R8 命名，后部仍有 Lite/Standard/Full、F8R4 旧表 | 自动生成能力/环境表，保留历史记录但不与当前发布说明混排 |
| R12 | P0，待验证安全与持久化 | 已有认证、开发者模式、配置临时文件/备份替换和恢复；全链路授权、跨文件事务、危险输出状态仍需组合验收 | 核验 API/规则/MQTT/导入等入口一致性，验证断电恢复与失败安全；不因单点已实现就判定全部闭环 |

R01 的准确边界：C3 仍有 `ChipConfig` 与基本引脚校验，**不能说 C3 完全没有保护，也不能说它已拥有同等完整的板级资源预检**。通用 S3 档案也不代表所有 S3 成品板的继电器、屏幕扩展器、电源和接线已被建模。

## 7. 开发板兼容性评估方案

### 7.1 现有构建范围

| 构建族 | 当前环境 | 下一阶段必核对项 |
| --- | --- | --- |
| ESP32，无 PSRAM | `esp32-F4R0`、`esp32-F8R0` | 普中专用资源与通用 ESP32 分离；4MB 裁剪、Flash/PSRAM 占脚、ADC/WiFi 约束、启动电平 |
| ESP32，有 PSRAM | `esp32-F8R8` | 外置内存是否真实可用、保留引脚、内部堆与 TLS 峰值 |
| ESP32-C3 | `esp32c3-F4R0` | 补板级资源档案与预检；GPIO/USB/UART、低内存、多外设竞争 |
| ESP32-C6 | `esp32c6-F4R0`、`esp32c6-F8R0` | DevKit 与其他 C6 板差异；UART/控制台、RMT/LEDC、无 PSRAM 预算 |
| ESP32-S3，无 PSRAM | `esp32s3-F8R0` | 不套用带屏高内存组合；启动、TLS、执行工作池与 SPI 共存 |
| ESP32-S3，有 PSRAM | `esp32s3-F8R8`、`esp32s3-F16R8` | Octal/其他内存接线、RGB DMA/缓冲、触摸/扩展器、屏幕与总线共存 |

当前 4MB 环境使用单 app 分区，8/16MB 环境有 A/B 布局；OTA 可用性按实际分区与构建宏判断。`esp32-F4R0` 当前明确裁剪实体屏幕和远程资源相关包，不能只看到共享 `unified_flags` 就声称所有环境功能相同。

### 7.2 建议的适配分层

| 层 | 内容 | 复用/演进方式 |
| --- | --- | --- |
| 芯片能力 | GPIO、ADC/DAC/Touch、UART、LEDC、RMT、PSRAM、DMA 等 | 继续以 `ChipConfig` 为集中入口；SDK 差异封装为能力，业务层不散落芯片判断 |
| 板卡档案 | 板型/修订号、模组/内存、电源、保留引脚、板载扩展器、端口别名、安全初值 | 演进 `BoardProfile`，先做编译期可信描述与公开配置模板，再考虑受限外部模板 |
| 驱动描述 | driverId、参数 schema、总线要求、通道、动作、采样下限、实例限制、预算 | 演进 `DriverRegistry`/`SensorDriverMetadata`；固件注册表是能力事实来源 |
| 实例配置 | 稳定 peripheralId、总线引用、地址、通道、校准、启用、故障策略 | 保持现有 `peripherals.json` 与旧 ID，加入可迁移的增量字段 |
| 应用配置 | 触发、条件、动作、字段绑定、展示、上报、故障处理 | 继续使用外设执行/面板/规则；换板优先改映射，不重建业务规则 |

不能把模板理解为动态加载任意驱动代码。**应用用户在已支持驱动范围内零代码；新增协议或未支持芯片仍需要开发者实现驱动并发布固件。** STM32、RP2040 等其他 MCU、Linux 主机等是独立移植项目，不进入本轮主计划。

### 7.3 每块板的最小交付包

- `boardId`、硬件 revision、所用模组、Flash/PSRAM/分区、板级依据和适用固件版本。
- 接线图、端口别名、保留/风险引脚、总线/中断/DMA/LEDC/RMT 等资源表。
- 板载器件及外扩器件列表、供电/电平/驱动器要求、开机和失联安全输出。
- 脱敏配置模板、配置迁移预览、最小自检流程、已验证/未验证矩阵。
- 未知板型不得绕过硬保留引脚；软件无法确认的接线、电气兼容性明确要求人工核验。

## 9. 零代码能力完善方案

### 9.1 单一能力描述，逐步收敛而非重写

在已有类型描述 API、驱动元数据、规则动作校验上补齐统一描述：

- 输入参数：类型、范围、单位、默认值、必填/条件可见、只读、危险等级和迁移规则。
- 通道输出：`sourceRef/channel/value/unit/quality/sampleTime/maxAge/error`，基于已有 Observation 模型统一，不新造第二套缓存。
- 动作能力：可执行目标、参数 schema、结果、是否幂等、超时、是否允许重试、故障安全策略。
- 资源要求：总线/地址/中断/DMA/PWM、最大实例数、最低采样周期、RAM/栈/Flash 成本范围。
- 运行状态：未编译、用户关闭、待生效、无实例、初始化中、运行、降级、离线、恢复中、失败。

描述符作为 Web 表单、API 校验、规则选项、模板和测试用例的共同来源。先覆盖新驱动和高频用例，再迁移旧类型；保留旧 JSON、数值枚举、外设 ID 和动作 ID，停用/删除后的引用必须能解释。

### 9.2 应用用户的标准流程

1. 选择板卡/模板；未知板卡从芯片能力开始手动映射，不自动猜测接线。
2. 功能配置显示依赖、预计资源、当前生效状态；只启用所需能力。
3. 添加外设：选择模块、接线、地址/通道；总线预检检查冲突，诊断读取显示值与质量。
4. 选择模板规则：触发 → 数据源/条件 → 动作 → 安全策略；普通场景无需手写 JSON、脚本或 C++。
5. 预览受影响外设/规则/资源；保存与生效分开反馈；失败不清空原配置。
6. 验证采样/执行结果，再绑定监控、大屏和 MQTT 字段；导出脱敏模板用于迁移。

优先模板：温湿度显示/上报、温控继电器（含回差/最小开停时间）、门磁/人体报警、液位/压力控制、土壤采样与灌溉、计数/流量、称重、Modbus 仪表、舵机限幅、断网记录。涉及泵阀/电机的模板默认禁用输出，完成接线与安全确认后才能启用。

### 9.3 外设执行需要统一验收的语义

- 既有平台/定时/事件/轮询触发分别验证；日历时间跳变、重复消息、规则相互触发不能造成无界循环。
- 条件支持并明确已有/新增范围：回差、去抖、持续时间、冷却、超时、失鲜、异常分支；缺失项才实施。
- 输出仲裁：规则、手动操作、MQTT、屏幕不得同时抢写同一执行器；给出优先级、租约/覆盖时长和可解释结果。
- 超时后的写动作不能无脑重试；电机、翻转、脉冲等非幂等动作必须先确认状态。
- 传感器异常不能转换成有效 0，缓存值必须带年龄；本地规则、显示、上报采用一致的质量策略。
- 现有调度下限定时 1 秒、轮询 5 秒；高频采样/精确运动由受控驱动完成，不通过把普通规则间隔调到毫秒实现。

### 9.5 首批零代码场景的可操作验收

以下不是新增一套规则引擎，而是用完整用户任务检验现有功能是否真正连通。先使用已有驱动，新增硬件另按 H1 排期；每个场景先完成离线/行为测试，实物部分仅在设备与操作范围获准后执行。

| 场景 | 用户只通过页面完成的操作 | 正常及异常验收 |
| --- | --- | --- |
| NC01 温控继电器 | 选择已支持温度传感器与输出，配置单位、阈值、回差、最小开停时间、安全状态，绑定显示/上报 | 阈值附近不抖动；传感器掉线/失鲜不按有效 0 判断；重启与恢复后的输出符合明确策略；真实温度/负载反馈单独核验 |
| NC02 数据采集与上报 | 配置已有传感器、采样周期、字段名/单位、MQTT 和监控显示 | 本地显示、规则、上报的数据源与质量一致；断网时队列有界，恢复按约定发送；旧缓存显示时间和失鲜，不伪装新数据 |
| NC03 Modbus 仪表 | 导入经过核对的只读模板，填写地址/串口参数，绑定工程量与展示 | 无需手写指令即可得到正确倍率/字序/单位；短帧、CRC 错误和超时可解释；未验证写命令不自动开放 |
| NC04 更换受支持板卡 | 从源方案导出，在目标板预览不兼容项、重映射接线/总线并保存 | 未改变业务含义的规则和逻辑外设 ID 尽量保留；冲突/缺驱动/资源不足在生效前明确阻止；不覆盖目标设备身份和凭据 |

共同验收条件：

1. 至少由一名未参与该功能实现的目标使用者，按提供的接线/配置说明独立完成场景；记录卡点、错误提示和恢复步骤，不以开发者代操作代替。
2. 普通流程不要求用户手写 JSON、脚本或 C++；高级入口保留，但不能用它绕过缺失表单来判定零代码通过。
3. 保存、待生效、真实采样、执行结果与物理反馈分别展示；至少验证一次重启恢复和一次相关故障恢复。
4. 用户能理解“为什么不可用、受什么影响、如何处理”；首次采集/导入等失败不清空有效旧配置，不把失败结果变成有效数值。
5. 记录人工试用与自动化结果，回归关联 V05/V08/V09/V14；缺实物或缺独立试用时保留待验证，不自动判为产品可交付。

## 10. 内存管理与长期稳定改进方案

### 10.1 先区分三类节省

| 方式 | 能节省什么 | 不能承诺什么 |
| --- | --- | --- |
| 编译裁剪 | 被排除代码/静态数据对应的 Flash 和静态 RAM，具体以 map/bin 为准 | Web 关闭开关不会自动缩小已烧录 bin 或扩大 app 分区 |
| 启动/按需初始化 | 未创建的驱动、缓存、连接、任务等动态 RAM；共享资源只分配一次 | 编译进来的静态数组、单例基础状态不一定消失 |
| 运行期停用/降级 | 确实停止并释放的动态资源，或通过降频减轻 CPU/分配压力 | 禁止新请求、暂停任务或隐藏菜单不等于对象已析构/栈已回收 |

首阶段沿用“保存并重启生效”，统一显示待重启。热启停只对生命周期明确、可安全释放的模块逐项开放，不作为所有功能首版的强制要求。保存失败时不能改变生效状态；运行保护不能擅自覆盖用户持久化选择。

### 10.2 评估清单

| 编号 | 检查内容 | 交付与验收方式 |
| --- | --- | --- |
| M01 | 内存口径 | 内部 8-bit DRAM free/min/largest、PSRAM、必要的 DMA-capable 内存分别记录；沿用 `MemoryBudget::dram8Free/dram8Largest`，不以总 heap 掩盖内部不足 |
| M02 | 启动与操作峰值 | 分阶段记录网络、认证、MQTT/TLS、外设、屏幕、规则、OTA/导入峰值；预算同时考虑最大连续块 |
| M03 | 按需分配 | 全可选关闭、仅打开功能但无实例、单实例、多实例、禁用重启、恢复启用六组对照；分别量静态、动态、共享和每实例成本 |
| M04 | 生命周期 | 外设创建/修改/删除、总线租约、工作任务、Ticker、回调、HTTP/SSE、TLS、屏幕缓冲、缓存逐项核对释放/引用；错误路径也测 |
| M05 | 有界容器 | 审计每个 String/vector/map/队列/结果/日志/历史/重试的长度、数量、TTL、溢出策略；不能因为用了动态容器就一律判泄漏 |
| M06 | 长寿命对象 | 复用既有固定工作池；减少高频 new/delete、大 String 拼接和多份 JSON 副本；大响应分页/分片，失败有明确结果 |
| M07 | 任务栈与时序 | 记录所有任务 HWM、峰值/最差路径、WDT；不盲目缩栈换 RAM。PSRAM 不假定适用于所有栈、DMA、ISR 或第三方对象 |
| M08 | 保护/恢复 | 准入→限流/降频→暂停可选采集→释放可选缓存→受控恢复；滞回、最小保持时间和有限重试，防止反复启停分配 |
| M09 | 输出安全 | 内存不足/总线失联时对每个输出明确保持/安全值/停止策略；继电器与电机不因自动恢复而意外动作 |
| M10 | 存储与闪存 | 沿用临时文件/备份恢复；评估跨文件一致性、写放大、日志轮转、满盘/损坏、掉电故障注入 |
| M11 | 可观测性 | 记录 allocation failure、各级保护次数/时长、跳过采样、队列拒绝、总线超时、连接错误、复位原因；采样器自身有频率和内存预算 |

现有明确边界包括：执行队列容量 16；classic/C3 一个执行 worker、C6/S3 两个；活跃定时/轮询任务上限 12；I²C 管理器客户槽 16；PointHistory 为 24 来源、每来源 10 点。它们是**代码配置上限，不是压力验收结论**。增加外设数量前要检查多个上限是否会先后碰撞，不能只改一个常量。

### 10.3 资源测量方法

固定固件、板型、配置摘要、网络/服务器条件和测量频率；记录至少三次冷启动及一次稳定运行基线。按实际板卡分无 PSRAM、小容量、带 PSRAM 控制器、屏幕节点四类负载，不强制所有板运行同一重负载。

每个可选功能记录：静态 Flash 增量、静态 RAM 增量、启动动态 RAM、稳态动态 RAM、操作峰值、最大连续块变化、栈 HWM、共享资源成本、每实例成本。固件 map/bin 与设备内存分开取证。

测量必须覆盖：无实例时不创建无用任务；配置停用后按声明方式生效；再次启用不丢配置；初始化失败/回滚不留租约；PSRAM 初始化失败时拒绝依赖功能并保持可诊断。功能页显示“预估范围/适用板型/测量版本”，不把常量相加伪装成实时占用。

### 10.4 建议验收目标（待 G00 测量后冻结）

- 零非预期复位、panic、WDT、已证实泄漏、越界或死锁；正常额定负载不靠反复内存降级维持。
- 启停/重配循环先做 100 次；冷/热启动各 20 次；故障注入独立窗口记录。以上是计划目标，不是本轮完成量。
- 额定负载下，最低内部堆/连续块必须满足实际功能的现有准入线及约定余量；不得为了“通过”降低保护阈值。
- 预热后同负载比较：建议 24 小时头尾稳定窗口中位数下降不超过 `max(2 KiB, 基线的 2%)`；同时不得有持续单向下降或不可解释的未回收对象。该阈值是初始筛查线，不是无泄漏证明，7 天窗口仍需检查趋势。
- 任务栈、UI 响应、采样抖动、恢复时限和丢样容忍按板型/场景冻结；平均值不能掩盖 p95/p99 与最差值。控制响应优先级不能被 Web 大响应/TLS/慢 Modbus 饿死。
- 网络/总线故障在声明重试周期内恢复；验证恢复前后的数据质量与输出状态。持续断网、物理断线可保持离线，但不能无界重试或伪造成功。
- 实际可用容量以“板型 + 功能组合 + 采样频率 + 外设/规则数量 + 可验证结果”发布，不宣称所有可编译功能同时开启也稳定。

## 13. 其他系统级优化建议

1. **协议与硬件模板库**：把 Modbus 仪表/继电器的寄存器、字序、倍率、单位、只读/写入限制做成可验证模板；缺少厂家映射时禁止猜值上线。通用 HTTP、Modbus TCP 等按真实发布能力单列，不与 Web 管理接口混淆。
2. **配置事务与版本化**：已有单文件原子写与备份继续复用；补跨功能/外设/规则/协议的引用校验、预览、提交和恢复证据，避免保存成功但依赖失配。
3. **运行诊断向导**：按配置→资源→驱动→物理采样→数据质量→规则→网络定位，显示失败阶段、外设/规则 ID、阻塞资源或依赖、最后有效采样时间、恢复状态和下一步建议。分别解释功能不能启用、数据失鲜、保存/升级失败与输出未动作，不能只显示“初始化失败”。诊断默认只读，不自动补写配置、重启设备或切换输出；测试输出需明确用户动作。
4. **安全维护**：核验首次密码修改、权限边界、危险操作入口、会话失效、固件完整性与来源策略、导出脱敏。Secure Boot/Flash Encryption 等需部署生命周期和密钥恢复方案后另行批准。
5. **可维护性**：大型管理器按行为边界小步拆分；共享解析/描述符减少 Web 与固件重复规则；增加分支行为测试，避免只靠源码字符串匹配。
6. **依赖与发布**：记录锁定版本/补丁、制品与 Web 资源哈希、兼容声明；升级 SDK/网络库单独回归，不为不明网络抖动随意改 TCP 参数。
7. **文档与冗余清理**：用已有保留审计工具盘点引用、用途、替代命令、保留期限；先列清单审核，历史失败证据、有效脚本与用户未提交文件不自动删除。
8. **低功耗是独立工作包**：休眠会影响 Web 可达性、MQTT、定时、采集和输出保持；在常在线稳定目标达标后，再按电池场景设计，不能只增加一个休眠按钮。

| 决定 | 建议默认选择 | 审核后影响 |
| --- | --- | --- |
| 首轮目标 | 现有四芯片家族与九环境的可靠产品化 | 不扩到任意 MCU，不承诺任意硬件自动适配 |

## 16. 与 ESPHome、Tasmota 的差距及借鉴边界

### 16.1 对标方法与总体判断

对标依据为两项目官方功能/开发文档与本计划中的当前源码检查，不是同硬件性能测试、用户规模调查或工业认证结论。此处不统计容易失真的驱动/模板总数，也不把项目有名、功能多等同于每个组合都可靠。

**结论：FastBee-Arduino 已有可复用平台基础，但在驱动/模板生态、扩展契约、配置复用、故障恢复的产品化和平台集成方面仍有明显差距。** 差距不只是再增加几个外设，而是一个新模块能否低成本接入、用户能否独立复用、出错后是否有可预测的恢复路径。该结论是结合下表的工程判断，不是第三方排名。

| 项目 | 主要优点与适合的方向 | 使用代价及不能外推的能力 | 对本项目的启示 |
| --- | --- | --- | --- |
| ESPHome | 配置校验、组件生命周期与共享实体接口清晰；packages/external components 支持复用与扩展；按配置生成固件，提供 Home Assistant Native API 接入。[E01][E02][E03][E06] | 新增组件或改变固件结构通常要修改配置、重新编译并升级；不能把这类流程当成所有操作均可在设备端点选完成，也不意味着它没有运行时控制或管理界面 | 学组件契约、配置复用和裁剪方法，不照搬为本项目所有用户都必须维护 YAML/编译环境 |
| Tasmota | 通用/功能变体固件、设备模板和 GPIO 映射便于复用已支持设备；规则与 ESP32 Berry 支持进一步扩展。[T01][T02][T03][T04][T07] | 必须匹配固件所含功能和设备接线；复杂逻辑可能需要命令、规则或脚本，模板存在不等于任意硬件即插即用 | 学模板、能力清单与恢复流程；高级脚本保留为扩展选项，不代替普通用户的表单配置 |
| FastBee-Arduino | 已有设备端 Web、外设执行、功能配置及 FastBee 接入基础，贴近现有采集/控制业务；在固件已包含且支持的能力范围内可通过配置复用。[S01][S08][S09] | 板卡预检、外设动作、资源/生命周期、迁移与实测闭环仍有缺口；新增驱动仍需开发和构建，部分配置需重启。当前优势是业务适配方向，不是通用生态或可靠性全面领先 | 保留现有架构和用户流程，先把常用方案做完整、可诊断、可迁移，再按真实需求扩硬件 |

不能简单描述成“ESPHome 只能写 YAML、Tasmota 只能敲命令、只有本项目有 Web”。这里比较的是核心配置/执行架构，不否认两者已有的管理、模板和安装界面。[E01][T01][T07]

#### 16.1.1 本项目优势的成立条件

- **已有基础，继续保留**：FastBee 业务接入、中文设备端配置、外设执行和按需功能门控是可复用资产。对当前业务可减少更换技术栈的范围，但尚未进行三方交付成本对比，不能声称所有场景都更省成本。当前发布通信能力以 MQTT/MQTTS、Modbus RTU 主站为边界，Web 管理接口不是通用 HTTP 上报，不能把协议名称或预留类型写成已支持能力。[S01][S08][S09]
- **潜在体验优势，必须验收后兑现**：把“选择板卡 → 选择模块 → 接线提示 → 资源检查 → 配置联动 → 展示/上报 → 故障解释”做成完整路径；由 V14 独立试用证明适用 NC 场景无需手改 JSON、脚本或 C++。有表单不等于流程已完整，新驱动开发、接线与必要标定仍是明确边界。
- **不作为领先宣传**：Web、规则、屏幕不是独占功能；运行时配置也带来依赖、资源分配、持久化和恢复成本。关闭开关不等于 bin 缩小或 RAM 已释放；在等价负载实测前，不声称比 ESPHome/Tasmota 更省内存、更快或更稳定。[E01][T01][T02][T03][T04]

2. Safe Mode、Safeboot、A/B OTA、配置备份是不同机制。Tasmota Safeboot 是 ESP32 范围内的特定分区设计，不代表本项目 4MB 单 app 环境可以直接得到 OTA；分区变更必须另行核验 Flash/文件系统、设备身份与回退，不在本次计划修订中执行。[E05][T05]

### 16.3 内存与稳定性：只作机制比较，不作未经测试的胜负判断

可以确认三者在构建/配置机制上有差异；不能据此断言 ESPHome/Tasmota 在本项目所有负载下必然更省 RAM、更快或更稳定。按配置编译有利于排除未使用代码，但实际 RAM 还受到 SDK、协议、日志、缓存、任务与功能组合影响。[E01][T02]

若需要量化对标，另行批准一个小范围试验：选择共同支持的无 PSRAM ESP32 和带 PSRAM S3，逐步运行“相同传感器采样 + MQTT”“增加等价本地继电器规则”“增加双方实际支持的总线设备”。记录各固件版本、SDK、编译选项、功能差异和接线；无法等价的项目标 N/A，不把缺功能造成的低占用当性能优势。

统一比较 bin/静态 RAM、内部 8-bit DRAM 最低值与最大连续块、实际任务栈口径、采样/控制时延、重连峰值、错误与降级持续时间以及同窗口长稳结果。ESPHome Native API 与本项目 MQTT 不是同一通信负载，若测试应分别列“共同 MQTT 基线”和“各项目惯用配置”，不能混成一张胜负表。

该三方实物基准属于新增专项，**未包含在原 31～49 人日主体估算内**；本次仅明确方法，不自动构建、部署或启动观察。

### 16.4 应借鉴什么，不应盲目复制什么

推荐路线是：**借鉴 ESPHome 的组件契约、配置校验和按需构建思路，借鉴 Tasmota 的设备模板与恢复流程，保留本项目“中文设备端配置 + 外设执行 + FastBee 接入 + 明确的工业采集/控制场景”。** 这是建议定位，不宣称这些单项功能独有或已超越两项目。Tasmota 已有 Web/规则、Berry/LVGL 等能力，因此“有网页、有规则、有屏幕”本身不能构成独占优势。[T01][T03][T04]

首阶段仍执行 G00～G03 的资源与可信性基础；G04/G05 优先把少量常见方案做得容易配置、可诊断、可迁移。H1 按真实需求补常用硬件，不把追齐全部外设目录作为短期目标。

本次不自动纳入：HA 专用集成、动态下载执行第三方驱动、Berry/其他 VM、云端按配置编译服务、任意芯片移植或分区改造。若用户希望做成面向更广泛社区的平台，再单独评估这些方向的价值、维护成本和安全边界。**原主体计划是产品化改进的工作量，不是追平两项目整个生态的承诺。**
