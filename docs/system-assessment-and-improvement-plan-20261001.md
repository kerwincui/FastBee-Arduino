## 1. 审核摘要

项目已经具备零代码嵌入式物联网平台的主体结构，不建议推倒重建。当前最需要的是把已有能力做成可验证、可迁移、资源可控的完整产品链路，而不是继续单纯增加外设类型名称。

本计划围绕四个目标展开：

1. **跨开发板**：芯片能力、整板接线、资源占用、驱动能力分别描述；更换板卡时尽量只调整板卡模板与接线映射。
2. **常用硬件零代码**：功能配置 → 外设配置 → 外设执行 → 数据/事件 → 联动/展示/上报 → 诊断，逐项验收闭环。
3. **按需内存**：区分编译裁剪、用户启用、依赖/预算准入、实例初始化、运行降级；“关闭选项”不直接等于“内存已经释放”。
4. **长期稳定**：以内部 DRAM、最大连续块、任务栈、队列上限、失败恢复和持续运行证据评价，而不是只看总可用堆或一次成功演示。

支持范围必须分级：首先稳定现有 ESP32、ESP32-C3、ESP32-C6、ESP32-S3 构建族；同芯片的不同开发板仍需单独核对接线、电源、外扩芯片和保留资源。其他 MCU 架构属于后续独立可行性工作，不承诺通过一份 JSON 直接适配。

## 2. 评估范围与证据等级

| 等级 | 含义 | 不能据此推断 |
| --- | --- | --- |
| E0 | 声明、枚举、菜单或设计文档存在 | 驱动或执行动作已实现 |
| E1 | 当前源码可定位到实际实现与调用链 | 测试已通过、实物正常 |
| E2 | 对应基线的主机/单元/离线浏览器测试通过 | 真实时序、电气行为、长稳 |
| E3 | 对应构建环境的固件编译与资源门禁通过 | 整板接线可用、部署完成 |
| E4 | 具体设备、固件哈希、配置和接线下实物验收通过 | 其他板卡或长期运行稳定 |
| E5 | 固定版本和负载下持续运行及故障注入验收通过 | 所有功能任意组合均安全 |

本次源码发现主要属于 E1，保留项可能仅为 E0。历史测试和设备报告只作线索，不能继承为当前工作区的 E2～E5 结论。源码评估结论将明确区分“已证实缺口”“待验证风险”“建议新增能力”。

全链路范围包括：设备监控、设备配置、网络设置、全部外设类型、外设执行、通信协议、设备大屏与实体屏幕、规则脚本、日志、用户管理、功能配置、导入导出、OTA、工厂恢复、发布与测试流程。

## 3. 已核实的基础

| 领域 | 当前工程基础 | 评估方向 |
| --- | --- | --- |
| 构建目标 | `platformio.ini` 有九个固件环境及 native 测试环境 | 整板支持与芯片构建支持分开；逐环境确认裁剪、分区和余量 |
| 外设建模 | `PeripheralTypes`、`PeripheralConfig`、`PeripheralManager` | 枚举、配置、初始化、执行、释放和展示是否对齐 |
| 资源预检 | `BoardProfile`、`PeripheralResourcePlanner`，已有 GPIO/总线/地址/UART/LEDC/RMT 等资源声明 | 服务与驱动是否全部参与；软件预检与真实分配是否一致 |
| 通用传感器 | `DriverRegistry`、`SensorDriverMetadata`、`SensorDriverCache` | 复用已有注册体系，补齐通道质量、生命周期和新增型号契约 |
| 功能配置 | `RuntimeFeatureManager`、`FeatureBudget` | 保留用户意图、依赖、预算、运行降级；核实实际 RAM 节省和生效方式 |
| 外设执行 | `PeriphExecManager/Executor/Scheduler/WorkerPool` | 规则与外设能力匹配、公平调度、失败隔离、有界队列 |
| 验证基础 | Host、Native、离线浏览器、构建矩阵、设备测试入口 | 区分测试性质与证据，不重复造一套门禁 |
