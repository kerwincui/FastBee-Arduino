# G01：执行动作目标契约收口

日期：2026-10-01。当前代码已从既有 feature-lifecycle 隔离区按基线哈希校验后局部合入主工作区；合入后 G01/G03/RTC 定向 60/60 通过，完整候选门禁终态以实施记录为准。不是 G01 完整参数描述符、所有动作运行验收或实物通过。

## 已复现差异

原 API 预检与规则保存各维护一份目标类型判断，行为存在差异：预检允许模拟输出执行 blink、普通非 passive 数字输出执行 PWM、扩展 IO 执行硬件 PWM/BREATHE；保存侧拒绝。反过来，编码器采样、PWM 舵机和既有模拟输出 PWM 被保存侧允许，旧预检却拒绝。这使“预检通过/失败”不能预测同一配置的保存结果。

行为回归直接编译生产函数，red-r3 首个差异为 action=2 / type=16 / expander=0 / passive=0。red-r1/r2 因测试夹具缺 ArduinoJson/数学头文件未进入行为测试，日志保留，不能当作生产行为失败证据。

## 实现范围

共享 PeripheralActionContract 纯函数统一“是否需要外设目标”“哪些类型可匹配”。以现有保存侧限制为准，不放宽扩展 IO、普通数字输出或 DAC 限制；保留动作 ID、现有配置、运行期资源/准入/命令验证。API 预检与保存/导入调用共同定义，没有为迁移新增硬件副作用。

通用 CALL_PERIPHERAL 的具体命令仍需现有执行器校验；“目标类型匹配”不等于当前驱动已初始化、动作已实现、预算通过或实际输出成功。系统/规则/事件/远程资源使用各自已有目标语义，不能当作普通 GPIO 目标。参数/schema、质量、运行能力描述和跨文件迁移仍有后续工作。

## 隔离证据

- 目标行为用例覆盖 35 个非保留动作 ID、100 个外设类型整数、4 种 expander/passive 组合，共 14,000 个目标比较和 35 个目标必需性比较；另有舵机、编码器、passive、扩展 IO、模拟输出与 RTC 的显式断言。
- 修复后单用例 green-r1 PASS，扩大规则事务/结果追踪/触发准入/生命周期合同 **34/34 PASS（1.342s，无跳过）**。日志在隔离区 artifacts/system-plan-g01-action-targets-20261001-green-r2.log。
- 主机编译只生成独立临时文件，没有运行隔离 PlatformIO、共享构建或串口。主工作区冻结候选的 Host/九环境运行期间没有修改其源码和测试输入；合入前须重新核对两个文件原哈希。
