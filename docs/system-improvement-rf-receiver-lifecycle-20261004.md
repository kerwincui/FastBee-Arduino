# RF RX 学习生命周期与按键持久化

本项是G04已有RF接收能力的故障闭环，和TX输出仲裁分别验收。这里描述待统一门禁验证的候选代码；不引用TX本地34项通过作为RX结果，不代表完整候选、真实接收、无线负载或长期运行验收通过。

## 已确认的问题与候选行为

- 原学习状态、键库修改和HTTP多次getter没有共同快照；现在接收状态、学习状态与缓存由同一生命周期mutex保护，HTTP一次取得对应快照，繁忙返回明确错误。
- 原派发规则时仍持有接收器mutex；现在在锁内保留一次派发占用，释放锁后派发。派发期间停止返回false且保留接收器；标记stopping后拒绝新检查、学习和begin，待派发结束重新停止。已经进入规则队列的动作不因此取消。
- 原begin可把单例静默绑定到另一个引脚，PM忽略begin失败、拆除也未停接收器；现在不同活动引脚返回false，PM传播失败，并以原引脚身份停止。拒绝初始化前不会先对新引脚调用pinMode。
- ISR与主循环使用同一跨核临界区交换脉冲；每次启用以代次token绑定callback。停用先关闭接收准入，再detach；迟到旧代次callback不能写入新代次缓冲。代次耗尽拒绝再次启动，不回绕复用。
- 学习剩余时间按uint32_t回绕计算。学习捕获只抑制该次事件，捕获后的正常接收仍可能触发规则。

## RF键库自己的文件事务

RF键库仍为`/config/rf_keys.json`数组，与IR的Manager配置存储路径不同。一次修改在RF模块内取得零等待mutation占用，重新读取原始文件，构造私有candidate，检查序列化长度，写入`.tmp`并逐字节读回，再比较原文件存在性及原字节，最后调用现有FileUtils原子rename；确认提交后才发布运行缓存。打开、短写、读回、已观察到的源变化或rename失败均不发布新缓存。rename失败保留主文件；源冲突保留外部写入和原缓存，不强行覆盖。

此流程不是覆盖所有文件入口的全局CAS。工厂恢复、文件管理器等不共享RF mutation占用；外部写者在最后比较和rename之间变化仍存在竞态边界。不得宣称任意外部并发导入/复位已受此事务保护。文件系统未初始化不能当作不存在的空键库。首次读取失败不会阻止原始码接收；重新begin、请求按键列表或后续键库修改会再次尝试读取，不在每次接收轮询中反复读坏文件。

最多40项，每项名称1～32个ASCII字母/数字/下划线/连字符/空格；code为不超过32位的完整十六进制字符串，可带0x前缀。bits为12～32且不得截掉有效高位；pulse为80～2000微秒，默认24位/350微秒。拒绝畸形结构、重复名称、内嵌NUL、尾随第二份JSON/非空白内容及超过8192字节的源文件。RX存储允许的脉宽下限是80；TX发送校验下限仍为100，保存了RX码并不保证能直接作为TX参数。

## HTTP结果

| 情况 | 结果 |
| --- | --- |
| 学习timeoutMs不是1000～60000的完整整数 | 400 |
| bits/pulse/name/code非法，或键库容量已满 | 400 |
| 接收器未准备、正在派发或停止中，不能开始学习 | 409 |
| 删除时确实不存在目标名称 | 404 |
| 文件、源冲突、mutation繁忙或状态快照未确认 | 503 |
| 修改/清空已确认提交 | 200 |

保留既有认证与开发者模式检查。按键管理不要求接收器已初始化。`RF_LEARN=1/PERIPH_EXEC=0`保留接收、学习与独立RF键库，只关闭规则派发；不依赖被关闭的Manager声明。`RF_LEARN=0`的真实driver与handler翻译单元均应由编译开关排除。
