# COM15 Modbus 与设备大屏修复记录（2026-09-25）

目标：ESP32-S3-F16R8，MAC 14:C1:9F:C1:52:D8，COM15。

## 发现与修改

1. RTU 接收等待原来只调用 yield()，任务仍处于可运行状态。在从站连续超时时，会增加低优先级 idle 任务不能运行、看门狗触发的风险。改为每轮阻塞一个 FreeRTOS tick；保留串口收包、帧间隔和超时检查。这是代码证实的风险，不能仅凭此认定用户此前重启的唯一原因。
2. 后台轮询在 1000 ms 超时、2 次重试配置下可能长时间占用总线；控制端获取总线只等 2000 ms。实机修复前状态读取返回 503 BUSY，耗时 2093 ms。现在后台事务在已完成当前报文、准备重试时检查排队控制，停止后台重试并释放总线；控制请求自身的重试策略保留。
3. 继电器状态接口严格使用实际通道数量，不把 4 通道请求扩成 8 通道；在窄整数转换之前校验从站、基址、数量及地址末端；不完整回包不再补成 false/关闭。
4. 大屏和 Modbus 控制面板区分忙碌与离线。503/429/BUSY 显示忙碌、状态未知，等待刷新；不会将忙碌算成自动刷新失败次数。成功回读后恢复状态。
5. 大屏监测值使用完整 Modbus 缓存及映射数据类型、偏移、倍率解码；SSE 已解码值独立保存，避免重复缩放。进一步拒绝布尔值、空白、对象、数组和无效质量数据冒充读数；无效 SSE 不会把设备恢复为在线。有效零值仍保留。
6. 当前工作树已有的异步继电器执行、单请求准入、20 ms 数字输入采样、异步日志落盘等修复保留并回归。本次冻结发布以 COM15 先前已验证版本为基线，仅叠加相关 C++ 和 Web 修改，避免包含其他设备正在开发的功能。

## 可复用实机验收

脚本 scripts/test-modbus-device.py 默认只读；通过环境变量 FASTBEE_PASSWORD 提供设备密码。脚本校验 MAC、采集串口异常、检查 uptime 单调递增、逐一解码启用的 Modbus 映射，并读取 di1、di2、do1。缺失数据会失败，不会填零通过。

    python scripts/test-modbus-device.py --url http://192.168.5.19 --expected-mac 14:C1:9F:C1:52:D8 --port COM15 --seconds 120 --out artifacts/com15-modbus-readonly-NEW

使用 C:/Users/kerwin/.platformio/penv/Scripts/python.exe，不使用系统 Python 2。继电器验收增加 --exercise-relay --relay-slave 6 --channel 0 --cycles 4。脚本先从现场配置确定协议和通道数，只有完整读到初始状态后才操作，逐次比对状态、检查其他通道不变，并在 finally 中恢复初始状态。无法读取初始状态时不发送控制命令。

COM15 串口操作和固件构建须通过 scripts/firmware-build-lock.ps1 串行执行。验收结果不能替代物理光电输入边沿响应测量、传感器标定或长时间稳定性测试。

## 部署前现场状态

设备恢复连接后，五个 Modbus 采集任务均为 error，无有效缓存；土壤温度 ADC 为 0，质量为 disconnected。此状态与“此前子设备已采集到数据”的现场状态不同，不能用当前空数据验证真实温湿度/空气质量数值。未擅自修改寄存器、倍率、供电或现场网络配置。
